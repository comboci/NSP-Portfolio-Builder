# NSP Portfolio Builder — Version 137 (page-first migration phase 1; source-only)

V137 introduces independent blank-page creation, a **system-wide page-template library with categories used only for finding templates**, and **project-local linked Custom Components inside the shared designer Toolbox**. The existing template records remain in SQLite `shared_templates`; category metadata lives in `shared_template_context`. Component definitions are stored in each project's canonical JSON payload. SQLite schema stays at revision 13, and image originals/backups are not reset by this commit.

A page created through the new flow has `masterTemplateId='none'` and `sectionId='CUSTOM'` as **internal compatibility sentinels**, not user-facing design concepts. Applying a template instantiates its elements onto a page; it does not maintain a live link back to the page template. Existing non-template elements on the page are retained. **Custom Components are different:** their instances store `componentId`, and the renderer resolves the current definition for every instance; per-instance geometry remains editable. Selecting ordinary local elements creates a named component, and Detach expands an instance into local objects. Private image ownership is project-scoped; publishing templates with private asset IDs is blocked.

**Not yet complete:** the legacy Master/Section data, normalization requirements, relational projections, some older screen handlers and backward-compatibility paths still exist internally. Removing them safely, validating nested image refs, designing scoped style defaults, and owner runtime acceptance remain tracked in Project Evolution. This release is **not** a claim of full legacy-model removal, successful execution or data reset. No Build, Test, static checker or Runtime was run by the assistant (DEC-006).

# NSP Portfolio Builder — Version 127 (TASK-038: fail-safe queued saves, source-only)

V127 tracks each queued Save Page, Save Project, and public-image rename by durable-write scope. A failed page remains an unresolved error even after another page or project write succeeds; no global **Saved** indication or successful flush is permitted until that failed scope receives an acknowledged recovery write. Native `WRITE_CONFLICT` continues to block writes without automatic stale replay.

The **Retry** action re-serializes the latest in-memory version of each failed page (or current project) under the existing SQLite CAS revision, never blindly replays an outdated payload, and refuses recovery when the owner project/page context is unavailable. ## V74 storage background (historical)

Version 74 preserves the Version 72 HTML editor, image library, crop/tiles, and browser IndexedDB storage, while changing **native Tauri/SQLite asset persistence**. The branch also retains the separate Project Evolution commits.

## Desktop storage

The Tauri app saves the project's complete editable *metadata and references* in SQLite. The binary original images and thumbnails are stored **once** in the application-local `storage/assets/` folder, identified by SHA-256. SQLite JSON records use `nsp-asset-v74:<sha256>` instead of Base64 image bodies. This also applies to automatic and named backup records. Files referenced by any backup are retained; asset garbage collection is intentionally **not** performed.

When loading a project or restoring a backup, the native backend verifies the image file and rebuilds the previous compatible data-URL representation for the existing editor. The portable JSON export generated in the editor still embeds images and is self-contained. The standalone HTML browser build **continues to use IndexedDB** and has no access to native SQLite.

### Non-destructive SQLite migration

The first native startup upgrades schema version 2 to 3 in a transaction, converting legacy Base64 payloads in projects, image metadata, templates, pages and automatic/named backups to immutable asset references. The old database tables are retained. If the conversion fails, SQLite rolls back; any content-addressed files already created remain safe. Because the new format is not recognized by V72, **do not downgrade the desktop app with an already migrated database**.

**Before first desktop launch:** make an independent backup of the whole `storage/` folder **including** `portfolio.sqlite3`, any WAL/SHM companion files, and `assets/` (close the application before copying). Keeping only the SQLite file will not preserve the images in V74. Exporting JSON from inside the app provides an independent portable backup.

cargo install tauri-cli --version '^2' --locked
